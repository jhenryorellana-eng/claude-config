### henryflow: applyExtractedCartaValues double-call in new_address worker
- The new_address worker calls `applyExtractedCartaValues` twice: once for address fields, once for court fields. Between the two calls the carta row's `updated_at` advances, so the second call does a fresh read and compares against the new timestamp. This is safe — each call is independently idempotent. `ensureCartaInstance` is also called twice (once per `applyExtractedCartaValues`), which is harmless (first call creates if needed, second is a no-op read).

### henryflow: `merged` returned by applyExtractedCartaValues reflects post-merge snapshot

### tindivo-v2: Supabase default EXECUTE grants apply to anon too, not just authenticated (catalog search feature, reviewed 2026-07-02)
- Confirmed via web research + this repo's own migration 0009 comment: "Supabase otorga EXECUTE a anon/authenticated explícitamente (default privileges)" — on Supabase, EVERY newly-created function in `public` gets EXECUTE auto-granted to BOTH `anon` and `authenticated` (and `service_role`), unlike vanilla Postgres where only PUBLIC gets it. If a migration's intent is "authenticated only, not anon" it MUST explicitly `revoke execute ... from anon` — omitting that revoke silently leaves anon with EXECUTE. Pattern to check on every new SQL function migration in this repo: does the revoke list include every role that should NOT have access, not just the ones the author remembered?
- `0052_catalog_search.sql`'s `f_unaccent(text)` needed EXECUTE for `authenticated` only (menu_items writes from the panel via PostgREST use that role) but never revoked it from `anon` — anon (the public API key) can currently call `POST /rest/v1/rpc/f_unaccent` directly. Low impact here (pure text transform, SECURITY INVOKER, no table access) but it's an unauthenticated compute-abuse surface with no length cap, and violates the least-privilege pattern this codebase otherwise follows precisely (0009's `current_business_id`/`current_driver_id` revoke from anon, keep authenticated).

### tindivo-v2: pg_trgm multi-word AND search — LIKE ALL(array) as filter, single most-selective LIKE for the index scan (good pattern)
- `search_catalog` RPC builds `v_patterns` (all query terms as `%term%`) and uses `LIKE ALL(v_patterns)` for correctness (AND semantics across words), but ALSO adds a redundant-looking `col LIKE ('%' || v_terms[1] || '%')` (longest term only) as a separate condition. This is intentional and correct: pg_trgm's GIN index accelerates a plain `LIKE '%x%'` predicate but does NOT get used for `LIKE ALL(array)` (that's evaluated as a post-filter). Picking the longest/most-selective term for the indexed condition, with the full `LIKE ALL` as an AND-filter for multi-word correctness, is the right pattern — don't "clean up" the apparent duplication.
- 2-char search terms are a known trigram-index weak spot (pg_trgm needs ~3 chars for meaningful trigrams; very short patterns degenerate toward scanning more of the GIN index, and `similarity()` scores for 2-char strings are low-precision). Acceptable at small-catalog scale; flag if catalog search ever needs sub-3-char precision at larger scale.


### usalatinoprime (henryflow): auto-repair-on-page-view is a check-then-act race with no DB guard (payments, reviewed 2026-07-18)
- Pattern: a Server Component page (`page.tsx`) calls a "self-healing" function on every request (`ensurePaymentPlanForCase`/`ensurePaymentPlansForClient`) that does `SELECT count(*) ... WHERE case_id=X` and, if zero, batch-`INSERT`s N rows. There is NO unique constraint on `(case_id, installment_number)` in `payments`, so two concurrent openers of the same case (two staff tabs, back/forward nav, or Next.js prefetch) can both pass the zero-count check and both insert, duplicating the whole installment plan. The code's own comment shows partial awareness ("already_has_payments es benigno — carrera con otra pestaña") but that only covers the case where the SECOND racer's OWN inner count-check catches it before its insert — not the case where both racers pass all checks and both insert (which produces silent duplicate rows with no error/log at all).
- Correct fix pattern for this codebase going forward: back check-then-act idempotency for financial row materialization with a real DB constraint (`UNIQUE (case_id, installment_number)` if that pair is truly a natural key) or a `pg_advisory_xact_lock(hashtext(case_id))` wrapped in a single RPC transaction — not just an app-level SELECT-then-INSERT. Before adding any such unique index here, audit `src/app/api/admin/payments/register/route.ts` (ad-hoc "register a payment" endpoint) which defaults `installment_number` to `1` for supplemental payments possibly on cases that already have a plan — a naive unique index could break that legitimate flow. Audit for existing duplicates first per this repo's own CLAUDE.md convention.

### usalatinoprime (henryflow): Next.js 16 App Router — writes inside a Server Component page render are real risk, not just style (2026-07-18)
- Confirmed via official Next.js 16 docs (nextjs.org/docs/app/guides/prefetching, "Troubleshooting > Triggering unwanted side-effects during prefetching", version 16.2.10 doc, project pins next@16.1.6): "If your layouts or pages are not pure and have side-effects... these might be triggered when the route is prefetched, not when the user visits the page." Official recommendation: move side effects to a Server Action from a Client Component, or a `useEffect`. There is also an open/recently-closed Next.js 16 regression, vercel/next.js#85489 ("Prefetch requests happen more than once on Next 16"), independent confirmation that prefetch-triggered duplicate RSC execution is an active, version-relevant concern for Next 16 specifically.
- Caveat found while auditing: per the same docs, a fully dynamic page (uses cookies/auth, no `loading.tsx` sibling) is NOT automatically prefetched by `<Link>` by default — so the everyday risk in this codebase is less "hover prefetch" and more "two staff members/tabs open the same case concurrently," which is a normal, frequent occurrence for a shared cobranza dashboard and does not depend on any prefetch nuance at all.
- Established review stance for this codebase: writes belong in Server Actions or Route Handlers, never directly in a page.tsx render body, even when the write is "idempotent" and wrapped in try/catch — the try/catch prevents a crash but does not prevent duplicate financial rows (see race entry above) and does not give a CSRF/method-safety boundary (GET-triggered mutation).

### usalatinoprime (henryflow): UI-only "confirm before charging" guard with no server-side enforcement (payments, BLOCKER class, reviewed 2026-07-18)
- `needs_reconciliation` flag pattern: the UI (payments-tab.tsx, collection-tab.tsx, bulk-payment-links.tsx) shows amber warnings telling staff "concilia antes de enviar el link, si no se le cobra de más al cliente" — but the actual money-moving endpoints (`/api/payments/create-checkout/route.ts` via `splitPendingForCheckout` in `src/lib/payments/build-plan.ts`, and `/api/admin/payments/generate-link/route.ts`) never read or filter on `needs_reconciliation` at all. `splitPendingForCheckout` treats ANY pending payment with `due_date <= today` as "charge now," which includes every needs_reconciliation row by construction (they were materialized already-overdue). A staff member can still click "Generar link" for a single to-reconcile case (only bulk "select all" excludes them), and any client with a pre-existing active `payment_tokens` row can self-serve pay at `/pagar/[token]` any time, completely bypassing the staff-facing warnings. Pattern to flag in future reviews of this codebase: whenever a new "risk flag" column is added to a financial table, verify EVERY code path that reads that table for a money-moving decision (checkout, invoicing, payouts) is updated to respect the flag — not just the human-facing dashboard. A grep for the flag's usage across `src/app/api/payments/**` and `src/lib/payments/**` is the fast way to check coverage.

### usalatinoprime (henryflow): deploy-order risk — column-dependent SELECT with explicit column list vs `select('*')` (reviewed 2026-07-18)
- When a PR adds a new NOT NULL (with default) column and ships code that both inserts it and explicitly names it in a `.select('col1, col2, needs_reconciliation')` list, deploying the CODE before the MIGRATION makes PostgREST reject that entire query (unknown column, PGRST204-style error) — Supabase-js returns `{data: null, error}` without throwing, so callers using `data || []` silently degrade to "no rows" rather than crashing. Net effect during the deploy gap: the feature this PR ships (plan auto-repair) actively fails AND an unrelated existing feature (payments list for that page) goes blank for ALL cases, not just the ones the PR targets. Pages using `select('*')` are naturally immune to this specific failure mode. Migration-first, code-second is the only safe order here; the reverse direction (migration applied, old code still running) is safe because old code simply doesn't reference the new column and the column has a DEFAULT.
