## Patterns learned

### usalatino-v2 (Next.js 15 + Supabase, modular monolith)
- **Architecture is strong on authz/secrets.** `requireActor()` → service `can()`/`requireCaseAccess()` first-line; env via typed `providerEnv()` (no scattered process.env); secrets never in NEXT_PUBLIC_*. Stripe webhook verifies signature over raw `request.text()` before any parse. RLS on every billing table. DB-backed idempotency: `webhook_events UNIQUE(source,idempotency_key)`, `ledger_entries` partial unique `(payment_id,kind)`.
- **RECURRING WEAKNESS — IDOR-on-null pattern.** Many billing fns guard with `if (caseId) await requireCaseAccess(...)` after `findInstallmentCaseId()`. When the installment→plan→contract→case chain yields null case_id (contracts.case_id IS nullable), authz is SKIPPED entirely for clients. Always flag `if (x) await requireAccess` — null must DENY, not bypass.
- **RECURRING WEAKNESS — webhook idempotency reimplemented inline.** Canonical helper `platform/webhook-events.ts claimWebhookEvent()` correctly returns fresh/duplicate/retry by checking `processed_at`. The Stripe route re-implemented it inline and returns 200 "duplicate" on ANY 23505 WITHOUT checking processed_at → a handler 500 followed by Stripe retry permanently drops the paid event (installment stuck in 'processing', card charged). Always verify webhook handlers reuse claimWebhookEvent, not a bespoke insert.
- **RECURRING WEAKNESS — no rate limiting on authenticated API.** `platform/ratelimit.ts` only has OTP/login/signing/express-interest limiters. No generic per-user/per-IP limiter; new /api/v1/* routes and server actions (Stripe checkout creation = creates Stripe customer+session = $ + Stripe customer-object spam; Zelle upload-url = signed URL generation) ship with zero rate limit.
- Price tampering: correctly prevented — UI sends only installmentId, amount always read from installments.amount_cents (DB). metadata org_id/case_id/installment_id only used as fallback lookup keys, never trusted to mutate amounts.
- OWASP Top 10 2025: A01 (Broken Access Control, now includes SSRF) remains #1; A03 Software Supply Chain and A10 Mishandling of Exceptional Conditions are new. The webhook retry-loss bug maps to A10.

HIGH-2 (IDOR null caseId) RESUELTO: 4 fns billing fail-closed con `if (actor.kind==='client' && !caseId) throw AuthzError('forbidden_case')`. MED-3 RESUELTO: orgId del ledger siempre desde findOrgIdForCase(caseId). LOW-1 RESUELTO. Migración 0019: índice único parcial payments(installment_id) WHERE status='pending' AND method='stripe' → mutex de BD para doble-checkout (insert-before-Stripe, 23505→PAYMENT_IN_PROGRESS).
- **NUEVO PATRÓN RECURRENTE — rate limit en call-site equivocado.** Cuando hay DOS superficies para la misma operación (un server action inline en page.tsx Y una action exportada en actions.ts), poner el limiter en una sola NO cubre la otra. Verlo en F6: limitBillingCheckout quedó SOLO en actions.ts (API-BIL-01 paralela) pero el UI cliente ejecuta el server action inline de pagos/page.tsx que llama svc.createCheckoutSessionForInstallment directo → SIN rate limit por el camino real. Contraste: limitBillingUploadUrl se puso DENTRO del service (getZelleProofUploadUrl) → cubre AMBOS call-sites. LECCIÓN: para rate limit/authz que deben cubrir todos los entrypoints, ponerlos en el SERVICE, no en cada action. Siempre rastrear qué call-site usa realmente el UI (grep onCreateCheckout/onX en la view).

### usalatino-v2 — F6-Ola2 (panel Andrium /finanzas) — audit Jun 2026
- **NUEVO PATRÓN RECURRENTE CRÍTICO — IDOR cross-org en mutations de staff (can() NO scopea por org).** `can(actor, module, action)` (platform/authz.ts) SOLO valida el permission-map; NO compara actor.orgId con el org del recurso. Las mutations de billing (confirmZellePayment, rejectZelleProof, registerZellePayment, waiveInstallment, rescheduleInstallment) hacen `can()` + findInstallmentById/findPaymentById por ID crudo vía createServiceClient() (service_role → RLS bypass total) y updateInstallment(id) — SIN verificar org. Un finance/admin de org A puede condonar/reprogramar/confirmar/registrar pagos de org B enumerando UUIDs. waiveInstallment es el peor (condona downpayment → afecta activación del caso + borra obligación financiera). El patrón CORRECTO ya existe en identity/service.ts: `if (target.orgId !== actor.orgId) throw new AuthzError('cross_org_access_denied')`. Las mutations de expediente (markPrinted/Shipped/Filed, getCompiledPdfUrl) llaman requireCaseAccess pero para STAFF eso solo hace can(actor,'cases','view') → TAMBIÉN org-blind. LECCIÓN: requireCaseAccess NO protege cross-org para staff; toda mutation que toca un recurso por ID debe resolver su org y compararlo con actor.orgId. Buscar siempre `findXById` + `update` sin org check.
- **Reads SÍ scopean por org (bien):** getCollectionMetrics/listDueCalendar/listOverdueForCollections/listPrintQueue pasan actor.orgId al repo y filtran `.filter(r => ...org_id === orgId)` en memoria (no en query — ver nota perf). Pero el filtro org está en JS tras traer filas; el query trae TODAS las orgs y filtra después → fuga si el `.filter` se omite + costo. collectionMetrics hace `.lte('due_date')` sin filtro org en query, filtra exigibles/overdue en JS — funciona pero trae cross-org rows a memoria. Preferir `.eq('cases.org_id', orgId)` en el query (como hace listPrintQueue).
- **Cron functions sin authz (latente):** markOverdues(_systemActor ignorado, NO llama can()), listReminderTargets(today) y recordReminderSent (sin can()) están exportadas del module index → callable desde cualquier app-layer. Hoy solo las llama el job installment-reminders (que SÍ pasa por verifyQStashSignature en el route ANTES de dispatch — bien). Riesgo: si alguien wira un server action a markOverdues, cualquiera dispara pending→overdue masivo. Defense-in-depth: gate con systemActor-only check.
- **QStash route bien:** verifyQStashSignature corre PRIMERO para TODOS los jobs (route.ts:88) antes de parsear/dispatch. installment-reminders hereda esa verificación. El job marca recordReminderSent ANTES de dispatch (evita doble-envío). insertNotificationIdempotent + dedupeKey por (type:installmentId:userId). PII (email) solo va al enqueue de deliver-notification, no se loguea.
- **PII en notificaciones de overdue:** register-consumers.ts wira installment.overdue → notifyFromEvent (Andrium staff) y → onInstallmentOverdue (kanban). El payload del evento lleva amountCents/dueDate/caseId/orgId pero NO nombre cliente; OK.

### usalatino-v2 — Etapa D Pre-Mortem (ai-engine) — audit Jun 2026
- **requireCaseAccess YA está org-scoped (CRITICAL-1 resuelto).** authz.ts:301 — staff: can('cases','view') + valida `cases.org_id === actor.orgId` vía service_role (DB autoritativa, no confía en JWT). Client: case_members. Esto CIERRA el patrón org-blind que documenté antes para el flujo que pasa por requireCaseAccess(caseId).
- **NUEVO PATRÓN CRÍTICO — IDOR por segundo-ID no validado contra el caso autorizado.** `assessPreMortemRisk(actor,{caseId,runId})` autoriza `requireCaseAccess(caseId)` PERO con runId explícito hace `findRunById(runId)` (UUID global, trae cases.org_id pero NO lo usa) y lee el memo de ESE run sin verificar `run.case_id === caseId`. Resultado: atacante pasa SU caseId (autorizado) + runId de OTRA org → lee memo ajeno (PII), lo persiste en su propio caso y lo recibe en la respuesta. cancelGeneration/regenerate/retryRunSameVersion SÍ lo hacen bien: `findRunById` y luego `requireCaseAccess(run.case_id)`. LECCIÓN: cuando una fn autoriza un recurso-A (caseId) pero opera sobre recurso-B (runId/docId), SIEMPRE verificar que B pertenece a A (o re-autorizar B). Buscar `findXById(idFromInput)` seguido de uso sin check de pertenencia.
- **Server actions = endpoints POST; autorizar cada uno por recurso.** runPreMortemAction (panel staff) solo hace requireActor()+requireCaseAccess; NO tiene gate `actor.kind==='staff'`. Un client miembro del caso puede invocarlo (action-id) y recibir el work-product interno (análisis de riesgo de denegación = estrategia confidencial no destinada al cliente). Next.js docs 2026: cada server action es entry-point separado, debe autorizar el RECURSO específico (IDOR). Para acciones staff-only añadir `if (actor.kind!=='staff') throw forbidden`.
- **RLS de tablas hijas de caso NO scopea por org (latente, sistémico).** case_pre_mortem_assessments SELECT usa solo `has_module('cases',false)` — y has_module() (0001:254) solo checa is_staff()+permiso, NUNCA compara org de la fila. Idéntico en ai_generation_runs (0004:579), case_status_history (0046), case_ownership_stage (0037). CONTRASTE: cases, case_members, ai_dataset_items_select SÍ scopean (`org_id = auth_org_id()`). App-layer está a salvo (service_role + requireCaseAccess org-scoped), pero vía PostgREST directo con JWT de staff (anon key es NEXT_PUBLIC) un staff de org A leería filas de org B. Hoy 1 org → sin impacto vivo; se vuelve real al 2º org. Fix de clase: SELECT con `exists(select 1 from cases c where c.id=case_id and c.org_id=auth_org_id())`.
- **maskPii (domain.ts:258) es regex por-patrón: SOLO SSN/A-number/passport.** NO enmascara nombres, direcciones, DOB, teléfono, email. Para un memo legal (prosa rica) esto deja pasar a Anthropic: nombre del solicitante, narrativa de persecución, fechas, direcciones. Es CONSISTENTE con la postura (Anthropic ya generó el memo con los mismos datos) pero el header "## LEGAL MEMORANDUM (PII masked)" es engañoso (overstatement). Gemini recibe memo CRUDO (embedText) y PDF crudo (extractRawTextFromStorage) — consistente con executeExtractionJob/translateDocument (Gemini ya recibe docs crudos). Recomendación recurrente: confirmar ZDR/DPA con ambos proveedores y no rotular "masked" lo que no lo está.
- **Logs limpios en Pre-Mortem:** logger.* loguea caseId/runId/model/tokens/cost, nunca el memo. Único matiz LOW: `logger.error({err,...})` en el fallo del crítico loguea el objeto err completo (un error del SDK Anthropic podría arrastrar fragmentos del request); preferir err.message.
- **Re-audit commit 01789ec — TODOS los hallazgos resueltos (BLOCK levantado).** CRIT-1: `if (run.case_id !== input.caseId) throw AuthzError('forbidden_case')` tras findRunById (rama runId) — cierra IDOR; test prueba 0 llamadas a Anthropic + 0 insert. HIGH-1: `if (actor.kind !== 'staff') throw AuthzError('wrong_kind')` en assessPreMortemRisk + getPreMortemAssessmentsForCase; isPreMortemEnabledForCase returns false (tab gating sin romper render). MED-1: migración 0056 org-scopea select+insert con exists(cases c where c.id=case_id and c.org_id=auth_org_id()) — SQL correcto, mismo patrón que ai_dataset_items_select. MED-2/LOW-1 ok. Tests de regresión asertan el comportamiento de seguridad (no smoke). Pendientes NO-bloqueantes: aplicar 0056 a prod (junto al deploy), confirmar ZDR/DPA Anthropic+Gemini, e issue de seguimiento para la clase RLS hermana (ai_generation_runs/case_status_history/case_ownership_stage siguen sin org-scope).

### usalatino-v2 — identity phone-as-identity refactor (audit Jul 2026, uncommitted diff)
- **Contexto:** identidad de cliente pasó de EMAIL → TELÉFONO. `provisionClientUser` dedup por phone; Auth usa email SINTÉTICO por teléfono (`syntheticAuthEmail`, dominio `clients.usalatinoprime.com`, email_confirm:true); login `signInWithPassword({phone})`; se ELIMINÓ `findClientByEmail`; `users.email` ahora nulable/repetible (schema 0001: email es `text` sin unique; solo `phone_e164` tiene unique index parcial global). RPC `search_clients_for_staff` (0062) SÍ org-scopea (`where u.org_id=p_org and kind='client' and is_active`).
- **PATRÓN RECURRENTE — refactor de identidad deja gate del CAMINO VIEJO.** Al mover la identidad email→phone, `loginClientByPhone` (service.ts:408) siguió gateando `if (!client || !client.email || !eligible) throw`. El email ya no se usa para firmar (signInWithPassword usa {phone}), así que `!client.email` es dead-weight que ROMPE el login de cualquier cliente aprovisionado SIN correo — que es exactamente lo que el refactor habilita. Fix: quitar `!client.email` de la condición (la elegibilidad = kind+is_active+case_member ya es el gate real). Los tests (service.test.ts:169) siempre mockean email no-nulo → la suite verde NO caza la regresión. LECCIÓN: tras un cambio de llave de identidad, grep TODOS los usos del campo viejo (`client.email`, `\.email`) y verificar que ningún gate/branch lo trate aún como requerido; exigir un test con el campo viejo en null.
- **Enumeración por nuevo endpoint = OK cuando es subconjunto estricto de uno existente.** `checkClientPhoneAction`/`lookupClientByPhone` reusa `searchClients` (mismo `can(clients:view)` + RPC org-scoped) y filtra a match EXACTO de phone → no añade superficie vs. el picker que ya expone name/email/phone/address a roles con clients:view. No es hallazgo nuevo. Matiz LOW de data-minimization: la action devuelve email+address aunque la UI solo usa `.name` en el banner de duplicado.
- **Self-heal de login es seguro (no takeover).** `updateUserById(client.id,{phone,phone_confirm,password})` con `client.id` resuelto por `findClientByPhone` (phone normalizado). El unique de phone en auth.users hace que si otro auth user ya tiene ese phone, updateUserById falle → sin retry → fail-closed. Email sintético: sin entrega (email_confirm:true, la app nunca manda a auth.users.email; los transaccionales usan public.users.email real), sin colisión (namespace separado, único por phone). derivePhonePassword sin cambios (HMAC phone+service_key).
- **LATENTE (multi-org, no introducido por el diff):** `provisionClientUser` Step 3 `findClientByPhone` es GLOBAL (phone unique es global, no per-org) y la rama de reuse de auth-shell hace `insertClientRows` upsert onConflict:id sin guardar `kind='client'`/org → bajo drift auth.phone vs public.phone_e164 podría pisar una fila public ajena. 1 org hoy. Guardar kind+org antes del upsert.

### usalatino-v2 — PR #36 phone country-code split (audit 2026-08-09, feature/phone-country-code-split)
- **NUEVO PATRÓN RECURRENTE — cambiar el FORMATO del state rompe validadores que cuentan dígitos.** Al pasar un input de texto crudo a un campo controlado sobre el valor COMPUESTO (`"+1"+nacional`), toda validación del tipo `phone.replace(/\D/g,"").length >= 10` queda con off-by-one: el "1" del prefijo cuenta como dígito → acepta 9 dígitos nacionales. Visto en `new-case-modal.tsx:522` (y el gate del dup-check en :324). Consecuencia: `normalizePhoneE164` recibe 10 dígitos ("+1305555010") y persiste "+11305555010" como `phone_e164` = identidad + credencial HMAC. Sin colisión (area code "1xx" no existe en NANP) pero sí fila rota irrecuperable. LECCIÓN: cuando un refactor cambia QUÉ contiene un state, grep TODOS los `state.replace(/\D/g,"").length`, `.trim().length`, `.startsWith` sobre ese state. El validador correcto era el regex exacto que ya existía (`isValidE164`, shared/phone.ts:26) — el login sí lo usa y por eso el login quedó bien.
- **PATRÓN — truncar en el parser convierte un error visible en un dato silenciosamente equivocado.** `parseNationalInput` (shared/phone.ts:156) hace `digits.slice(0,10)`: un internacional pegado ("+52 55 1234 5678") antes daba error del servidor y ahora compone "+15255123456", válido y falso. Brute-force de 22.4M cadenas: única ruptura de paridad vieja→nueva = nacional de 10 dígitos que empieza en "00" (el strip del prefijo "00" corre antes del check de longitud). Truncar silenciosamente en un campo-credencial es antipatrón; el parser debe dejar desbordar para que la validación falle.
- **PATRÓN PII — `autoComplete` heredado por un componente compartido entre superficie del CLIENTE y del STAFF.** `PhoneField` hardcodea `autoComplete="tel-national"`; en /entrar es correcto (número propio), pero en los formularios de staff (alta de caso, editor de contrato, leads, citas) mete teléfonos de CLIENTES en el perfil de autofill del navegador del staff y sugiere el de un cliente al crear otro. Antes esos inputs no declaraban autoComplete. Regla: un componente de campo compartido debe recibir `autoComplete` por prop, default "off".
- **`public.normalize_phone` (0001_identity.sql:48-51) es MÁS PERMISIVO que el TS**: tercera rama `left(raw,1)='+' and length(digits) between 7 and 15 → '+'||digits`, y `return raw` como fallback. `users.phone_e164` solo tiene UNIQUE index (0001:93), NO hay CHECK de `^\+1\d{10}$`. ⇒ valores no canónicos son representables; no asumir que todo phone_e164 es "+1"+10. Query de verificación (prod, pedirla a db-architect): `select count(*) from public.users where phone_e164 is not null and phone_e164 !~ '^\+1\d{10}$'` debe dar 0.
- **Verificado limpio en este PR:** 0 archivos en `supabase/` o `src/backend/` (usar `origin/main...HEAD`, el `main` local estaba stale y inflaba el diff con 3 PRs ajenos); `derivePhonePassword`/`normalizePhoneE164`/`normalize_phone`/`E164_US_REGEX` intactos (deuda #14 SIN CAMBIOS, ningún uso nuevo de service_role como material criptográfico); fricción del editor de contrato intacta (banner + dialog + `phoneE164` solo se envía si `phoneDiverged && normalizedPhone` → formulario intacto NO rota credencial); PII solo rango ficticio 555 (305-555-01xx / 786-555-0101) y harness `/admin-preview` con VM mock; RNF-036 OK (`getBridge().share.copyText`, único `navigator.clipboard` está en un spec Playwright); MCP supabase sigue pineado a dev por `--project-ref`.
